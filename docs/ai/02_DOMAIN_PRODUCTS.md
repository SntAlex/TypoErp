# Доменная модель и правила модуля «Товары» (Products)

## 1. Правила нормализации (`StringNormalizer`) и кроссплатформенной валидации имен
### 1.1. Нормализация строк
Вся работа с названиями первичных тегов, артикулов, префиксов, форматов, категорий и непервичных тегов использует единую нормализацию:
1. Обрезаются пробельные символы по краям (`Trim()`).
2. Любые последовательности из 2 и более пробельных символов внутри строки заменяются на один обычный пробел `' '`.
3. Строка переводится в нижний регистр с инвариантной культурой (`ToLowerInvariant()`).
- *Пример:* `"  МоЙ   ТЕг \t "` -> `"мой тег"`.

### 1.2. Нормализация имен файлов
Для файлов (обложек, видеообложек, файлов сборки) нормализуется отдельно имя без расширения и само расширение:
- `NormalizedFileName = Normalize(Path.GetFileNameWithoutExtension(name)) + Path.GetExtension(name).Trim().ToLowerInvariant()`
- *Пример:* `"  Cover_1   (2).JPG "` -> `"cover_1 (2).jpg"`.

### 1.3. Кроссплатформенная валидация имен папок и файлов (`FileSystemNameValidator`)
Имена папок и файлов должны быть валидны одновременно в **Linux, Windows и macOS**:
- Запрещены символы: `<`, `>`, `:`, `"`, `/`, `\`, `|`, `?`, `*`, а также управляющие символы ASCII (`0x00`–`0x1F`).
- Имя не может состоять только из точек (`.` или `..`) и не может заканчиваться точкой `.` или пробелом (ограничение Windows).
- Запрещены зарезервированные имена устройств Windows (без учета регистра, как само имя, так и имя до первой точки): `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`.

### 1.4. Системные и игнорируемые файлы
- Внутри папки товара создается системный файл `.typoerp_id` (содержит `Guid` товара). Он не считается файлом сборки.
- В конфигурации `ProductsStorageOptions:IgnoredFilePatterns` задается список игнорируемых файлов и масок ОС (по умолчанию: `.typoerp_id`, `thumbs.db`, `desktop.ini`, `.ds_store`, `~$*`, `.*`). Игнорируемые файлы не участвуют в валидации префиксов сборки.

## 2. Автоматическая нормализация на диске при синхронизации
При запуске синхронизации (`ProductSyncService`):
1. Система обходит папки первичных тегов, папки артикулов и файлы внутри них.
2. Если текущее имя папки или файла на диске отличается от его нормализованной формы (например, `"  Мой  Тег "` вместо `"мой тег"`, или `"CARD_1.PDF"` вместо `"card_1.pdf"`), система **автоматически переименовывает** папку/файл на диске в нормализованный вид.
3. **Обработка конфликтов авто-нормализации:**
    - Если переименование невозможно (например, в одной папке лежат `"Мой Тег"` и `"мой  тег"`, которые нормализуются в одно имя `"мой тег"`, либо в имени есть запрещенные символы, либо ошибка доступа), система **не прерывает** синхронизацию.
    - Проблемная папка/товар/файл заносится в БД со статусом `IsValid = false` и кодом ошибки (например, `NormalizationConflict`), чтобы пользователь увидел его в таблице на сайте и исправил через UI.

## 3. Иерархия в хранилище (`IProductStorage`)
Корень хранилища задается в конфигурации (`ProductsStorageOptions:RootPath`).
Если корневой путь не существует или недоступен — сайт блокирует операции с товарами и выводит понятное сообщение об ошибке.

Структура каталогов:
`<RootPath> / <Первичный Тег> / <Артикул> / <Файлы товара + .typoerp_id>`

### 3.1. Первичный тег (Primary Tag)
- Папка 1-го уровня в корне хранилища. Обязателен для каждого товара (папки/файлы, лежащие прямо в корне вне первичного тега, фиксируются как невалидные).
- **Ограничения (из конфигурации):**
    - Максимальная длина нормализованного названия: по умолчанию `200` символов.
    - Максимальная вместимость (количество товаров внутри): `MaxProductsPerPrimaryTag` из конфигурации.

### 3.2. Товар и Артикул (Product & Article)
- Папка 2-го уровня внутри папки Первичного тега. Название папки = нормализованный Артикул.
- Имеет уникальный внутренний `ProductId` (`Guid`), который хранится в `.typoerp_id` и в PostgreSQL.
- **Правила валидации артикула:**
    - Нормализованный артикул обязательно должен содержать **хотя бы один пробел**.
    - Максимальная длина нормализованного артикула: по умолчанию `60` символов (из конфигурации).
    - Кроссплатформенно валидное имя папки.
- **Черновики товаров:** Разрешено создавать через UI «пустой» товар (без файлов сборки). Папка и `.typoerp_id` сразу создаются на диске, а сам товар в БД помечается как `IsValid = false` (причина: `MissingAssemblyFiles`) до тех пор, пока пользователь не загрузит файлы сборки.

### 3.3. Выделение префикса файла (`FilePrefixExtractor`)
Для каждого неигнорируемого файла в папке товара вычисляется **Префикс (Prefix)**:
- Берется нормализованное имя файла без расширения.
- Ищется первое вхождение пробела `' '` или нижнего подчеркивания `'_'` (смотря что встретится раньше).
- Берется подстрока до найденного разделителя (или всё имя без расширения, если пробела и `_` нет) в `ToLowerInvariant()`.

### 3.4. Классификация файлов товара
1. **Обложки (Covers):**
    - Префикс равен `"cover"` (примеры: `cover_1.jpg`, `cover (2).tif`, `cover.png`).
    - Расширение должно входить в `AllowedImageExtensions` из конфигурации (например: `.jpg`, `.jpeg`, `.png`, `.tif`, `.tiff`, `.webp`).
2. **Видеообложки (Video Covers):**
    - Префикс равен `"video"` (примеры: `video_1.mp4`, `video (2).mov`, `video.mkv`).
    - Расширение должно входить в `AllowedVideoExtensions` из конфигурации (например: `.mp4`, `.mov`, `.mkv`, `.avi`, `.webm`).
3. **Файлы сборки (Assembly Files):**
    - Все остальные файлы (кроме обложек, видеообложек и списка игнорируемых).
    - **Правило единого префикса:** Все файлы сборки внутри папки одного товара обязаны иметь **одинаковый префикс**, и должен присутствовать хотя бы один файл сборки.
    - Если префиксы файлов сборки отличаются или файлов сборки нет — товар имеет `IsValid = false`.

### 3.5. Категория (Category) и Формат (Format)
1. **Категория (`Category`):**
    - Выводится автоматически из единого префикса файлов сборки товара (например, префикс `"card"` -> код категории `"card"`).
    - Пользователь может задать для категории понятное отображаемое название (`DisplayName`, например `"Наклейки"`).
2. **Формат (`Format`):**
    - Выводится автоматически из нормализованного артикула: **подстрока до первого пробела** (например, из `"45к артикул тест"` -> код формата `"45к"`).
    - **Иерархия и уникальность:** Форматы лежат строго внутри Категории. Уникальность формата определяется парой `(CategoryId, FormatCode)`. Формат `"45к"` в категории `"card"` и формат `"45к"` в категории `"poster"` — это **два разных формата** со своими настройками и тегами.
3. **Мягкое удаление (Soft Delete):**
    - При удалении или изменении товаров, если у формата или категории больше не осталось привязанных товаров, они помечаются как `IsDeleted = true` (мягкое удаление). При повторном появлении товара с такой категорией/форматом запись автоматически восстанавливается (`IsDeleted = false`), сохраняя старый `DisplayName`, настройки и непервичные теги.

### 3.6. Непервичные теги (Secondary Tags)
- Необязательные теги в PostgreSQL (нормализуются по общим правилам).
- Могут назначаться на: **Товары**, **Форматы**, **Категории** (связи многие-ко-многим).

### 3.7. Хэширование (`XxHash64`) и Diff-синхронизация
- Для каждого файла товара вычисляется и хранится в БД 64-битный хэш `XxHash64` (в виде hex-строки или `ulong`) и размер файла в байтах.
- При редактировании товара через сайт или при синхронизации с диском перезаписываются и пересчитываются только реально изменившиеся/новые файлы.
